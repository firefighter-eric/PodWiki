# Web 阅读器性能基准

本文记录 2026-08-07 的节目与单集导航加速，以及 2026-08-08 的全文搜索优化，回答每一层改动分别减少了多少工作、带来了多少响应时间收益，以及哪些改动只改善反馈而不缩短网络时间。

## 结论

以下页面导航数据来自同一台机器、同一份 43 集内容、相同 Next.js 16.3.0 production 模式，候选版本相对 `origin/main` 的 `59a16a4`：

| 页面 | 旧版 TTFB 中位数 / p95 | 新版 TTFB 中位数 / p95 | 中位数降低 | 约等于 |
| --- | ---: | ---: | ---: | ---: |
| 节目页 | 58.88 / 65.72 ms | 1.00 / 1.33 ms | 98.29% | 58.6× 更快 |
| 单集总结 | 58.37 / 69.63 ms | 1.03 / 1.29 ms | 98.23% | 56.6× 更快 |
| 单集逐字稿 | 61.80 / 71.91 ms | 2.32 / 2.74 ms | 96.24% | 26.6× 更快 |

旧版三个页面都是每次请求动态渲染，响应头为 `private, no-cache, no-store`。新版预生成 5 个节目页、43 个总结页和 43 个逐字稿页，响应头为 `s-maxage=31536000`；请求由静态产物响应，不再等待服务器读取 Markdown 和渲染 React。

搜索使用另一组进程重启测量，不与上面的页面 TTFB 样本混算。旧搜索在进程预热后，不同查询仍需 117.72–122.67 ms；轻量索引版本降至 1.78–5.69 ms，四个热查询平均从 119.79 ms 降至 3.55 ms，降低 97.03%。首次冷查询仍需构建索引，只从 198.67–207.29 ms 降到 183.12 ms；重复 `RSI` 查询命中进程内 LRU 后为 1.22 ms。

## 各部分收益

### 1. 目录加载器：不再解析全库逐字稿

旧版的目录请求会调用同一个全量加载器。它读取 137 个选中 Markdown、7.734 MiB，并解析 56,990 条带时间码的原文或译文。新版将目录数据与正文数据分开：

| 加载场景 | Markdown 文件 | 读取量 | 带时间码段落 | 相对旧版节省 |
| --- | ---: | ---: | ---: | --- |
| 旧版全量加载 | 137 | 7.734 MiB | 56,990 | 基线 |
| 新版节目/单集目录 | 91 | 1.025 MiB | 0 | 文件 33.6%；字节 86.7%；段落解析 100% |
| 新版目标单集：Kimi K3 | 4 | 0.157 MiB | 932 | 文件 97.1%；字节 98.0%；段落解析 98.4% |
| 新版双语单集：李沐 | 5 | 0.078 MiB | 680 | 文件 96.4%；字节 99.0%；段落解析 98.8% |

目录仍读取节目 README、单集 README 和总结简介，因此文件数只减少 33.6%；真正昂贵的逐字稿读取与正则解析被完全移出目录路径。目标单集只读取自己的 README、总结、选中逐字稿和可选译稿，不再跨单集读取。

静态页面部署后，上述节目页和单集页在请求时的 Markdown 文件读取数进一步变为 **0**；加载器只在构建、开发模式和仍为动态的搜索接口中运行。

### 2. 节目页：动态渲染改为 SSG

节目页增加静态参数生成，5 个节目页随构建预生成。它的同机 TTFB 中位数从 58.88 ms 降至 1.00 ms，降低 98.29%；p95 从 65.72 ms 降至 1.33 ms，降低 97.98%。

### 3. 单集总结：移除请求期 `searchParams`

旧单集页读取 `searchParams` 来决定总结或逐字稿，Next.js 因此必须在请求期动态渲染。新版让基础路径固定为总结页，并预生成全部 43 个总结页。TTFB 中位数从 58.37 ms 降至 1.03 ms，降低 98.23%；p95 降低 98.14%。

### 4. 单集逐字稿：独立静态路径

逐字稿迁移到 `/shows/[showId]/episodes/[folder]/transcript`，同样预生成 43 个页面。TTFB 中位数从 61.80 ms 降至 2.32 ms，降低 96.24%；p95 降低 96.18%。

逐字稿页面比总结页大，因此静态响应仍需要约 2.3 ms，而不是 1 ms 左右。旧的 `?view=transcript` 保留 308 兼容跳转；站内链接已全部使用新路径，不承担这次跳转成本。

### 5. Loading 边界：改善感知，不计作网络加速

节目与单集路由新增可访问的 loading 状态。骨架延迟 120 ms 才淡入：快速静态导航不会闪屏，超过 120 ms 的网络等待会出现“正在载入”反馈。

这项改动不减少 TTFB，原始加速记为 **0%**；它解决的是慢网或缓存未命中时“点击后没有反馈”的感知问题。

### 6. 日期右移与动画整理：布局收益，不计作请求加速

节目名与日期右对齐，为多人名保留更多首列宽度。390 px 浏览器验证中，人物名与右侧元数据保持 14 px 间距，页面横向溢出为 0。

这项 CSS 调整不减少网络或服务器时间，原始加速同样记为 **0%**。

### 7. Vercel 函数追踪范围

此前 `/api/search` 使用 `shows/**/*.md`，把正式内容和 `asr/` 中间稿一起带入函数。旧构建实际追踪 188 个内容文件、14.59 MiB，其中 45 个 `asr/` 文件占 6.86 MiB。新版只追踪节目 README、单集 README，以及单集根目录下的正式 `summary*.md`、`transcript*.md` 和翻译稿：当前为 143 个文件、7.74 MiB，`asr/` 文件数为 0。

函数内容包因此减少 45 个文件、6.86 MiB；文件数减少 23.9%，字节减少 47.0%。这主要降低部署和冷启动需要携带的文件范围，不直接计入上面的页面 TTFB 百分比。

### 8. 全文搜索：预小写文档索引与有界 LRU

旧搜索先构造全部完整 `Episode` 对象，再在每次查询时对标题、总结、逐字稿和译稿重复执行 `toLocaleLowerCase()` 与全段过滤。新版在每个服务器进程内只构建一次专用搜索文档：保留检索与结果展示所需字段，预先生成小写文本；逐字稿和译稿找到每集前 3 个匹配后停止继续扫描。查询结果使用 64 项 LRU，键按大小写归一。索引构建失败时会清除 Promise，下一次请求可以重新构建，而不是永久缓存失败。

API 结果只来自公开静态内容，因此响应改为 `public, max-age=0, s-maxage=300, stale-while-revalidate=86400`。进程内 LRU 负责同一实例上的重复查询，`s-maxage` 则允许生产 CDN 在 5 分钟内复用相同 URL 的结果；本地 `next start` 测量只验证了前者，不把尚未测量的 CDN 命中算入收益。

| 查询场景 | 旧版 | 新版 | 降低 |
| --- | ---: | ---: | ---: |
| 冷进程首次 `RSI` | 198.67–207.29 ms | 183.12 ms | 7.83%–11.66% |
| 热进程 `Kimi` | 120.78 ms | 4.10 ms | 96.61% |
| 热进程 `AI` | 117.72 ms | 1.78 ms | 98.49% |
| 热进程 `机器人` | 117.99 ms | 2.64 ms | 97.76% |
| 热进程无结果 | 122.67 ms | 5.69 ms | 95.36% |
| 热进程四项平均 | 119.79 ms | 3.55 ms | 97.03% |
| LRU 重复 `RSI` | 未单独采样 | 1.22 ms | 不计算 |

五个对照查询的旧版与新版响应体字节数逐项相同：`9966 / 9888 / 9317 / 12224 / 2`，同时保留每集最多 3 条逐字稿、最多 3 条译稿、全局排序后最多 24 条结果以及原时间戳链接。这里的时间是 API 请求总时间；搜索框仍有 180 ms 输入防抖，不应把它误算为服务器查询时间。

RSS 只能作为进程级边界观察，不能替代堆快照。旧版一次冷构建后记录为 205,424 KB，另一次查询序列后记录为 157,728 KB；新版请求后为 211,024 KB，等待 5 秒后为 157,808 KB。两版最终观测值都约 158,000 KB，但旧版两个值来自不同进程生命周期，因此不能据此计算严格的内存降幅。新版减少的是每次查询的 CPU 分配、响应时间和函数追踪包体，**不宣称降低常驻内存**。

## 浏览器结果

候选版本本地 production 环境的真实浏览器测量：

| 操作 | 点击到目标内容完成两帧绘制 |
| --- | ---: |
| 节目页进入另一单集总结 | 20.4 ms |
| 总结切换到逐字稿 | 27.7 ms |

桌面与 390 × 844 移动端均无控制台错误或警告，移动端无横向溢出。这里记录的是候选版本绝对值；跨网络的生产环境数据在上线验收时另行测量，不与本地数据混算百分比。

## 代价与未优化部分

- 工作从请求期转移到了构建期：当前构建预生成 97 个页面，静态页面生成约 1.3–1.5 秒。
- 使用未压缩的 `Accept-Encoding: identity` 测量时，新版 HTML 体积比旧版增加：节目页 7.8%、总结页 11.1%、逐字稿 2.4%。本次收益来自消除请求期计算和启用缓存，并非缩小 HTML。
- `/api/search` 的冷进程仍需读取正式总结、选中逐字稿和翻译稿并构建索引，因此首次查询仍约 183 ms；当前优化没有消除冷启动工作。
- 热搜索仍按搜索文档线性检查内容，只是避免了重复小写转换，并在每集取得 3 个段落后提前停止。内容增长到数百集后，应重新评估构建期倒排索引或独立搜索服务，而不是把当前 1.78–5.69 ms 外推到任意规模。
- 进程内索引保存原文与预小写文本，垃圾回收后的 RSS 与旧版基本持平；若未来把内存作为目标，需要单独做堆快照和索引编码实验。
- 总结页在构建期仍读取目标逐字稿，以生成相关片段与章节；它不再发生在用户请求期。

## 测量方法

- 基线：`origin/main` 的 `59a16a4`。
- 候选：本次静态路由与内容加载拆分后的工作树。
- 两份源码分别独立执行 `npm run build` 与 `next start`。
- 同机回环地址、HTTP keep-alive、单连接、`Accept-Encoding: identity`。
- 每条路由预热 5 次，再交替请求旧版和新版各 40 次；p95 使用 nearest-rank。
- Node.js `v25.8.2`；页面内容在两份构建中相同。

搜索旧版是 2026-08-08 本轮搜索修改前的工作树，不使用页面表格的 `59a16a4` 基线。搜索 A/B 使用相同内容和 production 构建，依次在干净重启的本地 `next start` 进程请求 `RSI`、`Kimi`、`AI`、`机器人`、无结果词，再重复 `RSI`。冷查询记录重启后第一次非空请求；其余是同进程单次样本，不是 40 次分布，也不提供 p95。函数追踪体积来自构建产物 `.next/server/app/api/search/route.js.nft.json`，将其中实际存在的 `shows/` 文件解析为绝对路径后求和。RSS 使用 `ps` 在多次独立运行中采样；新版额外等待 5 秒复测，旧版的瞬时值与后续值不属于同一进程，因此这些数字只用于标示观测边界。

每次重启旧版或新版 production 服务后，可用同一命令复现搜索请求序列；第一项才是冷查询：

```bash
SEARCH_BASE=http://127.0.0.1:3014 node --input-type=module <<'NODE'
const base = process.env.SEARCH_BASE;
for (const q of ["RSI", "Kimi", "AI", "机器人", "不存在词条xyz", "RSI"]) {
  const startedAt = performance.now();
  const response = await fetch(`${base}/api/search?q=${encodeURIComponent(q)}`);
  const body = await response.arrayBuffer();
  console.log(JSON.stringify({
    q,
    status: response.status,
    ms: Number((performance.now() - startedAt).toFixed(2)),
    bytes: body.byteLength,
    cacheControl: response.headers.get("cache-control"),
  }));
}
NODE
```

启动旧版和新版 production 服务后，可用仓库脚本复现 HTTP 部分：

```bash
cd apps/web
OLD_BASE=http://127.0.0.1:3011 \
NEW_BASE=http://127.0.0.1:3012 \
PERF_WARMUPS=5 \
PERF_SAMPLES=40 \
node scripts/benchmark-routes.mjs
```

百分比使用 `(旧值 - 新值) / 旧值 × 100%`。本地 A/B 用于隔离代码变化；生产验收必须另看 Vercel 缓存响应头、真实网络、DOM、交互、响应式布局和浏览器控制台。
