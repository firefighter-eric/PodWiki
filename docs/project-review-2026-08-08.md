# PodWiki 项目全面审计与修复

日期：2026-08-08
范围：产品体验、可访问性、内容正确性、安全、性能、SEO、测试与工程门禁。

## 审计方法

- 从 `/shows`、节目页、单集总结、逐字稿和全文搜索走查主要用户路径；覆盖桌面与
  390 px 移动视口、键盘焦点、文字复制、前进后退和窗口缩放。
- 复核 Next.js 路由静态化、客户端边界、预取、函数文件追踪、搜索热路径和构建产物。
- 对 Markdown 渲染、内容路径、单集元数据、工作流状态、时间码和稳定 ID 做恶意或
  非法输入回归。
- 执行 Python 单元测试、仓库内容校验、Web lint、TypeScript、Vitest、生产构建、
  依赖 advisory 检查和 Git whitespace 检查。

## 已修复问题

### P1：会直接影响读者或内容安全

1. **侧栏来源范围与当前单集解耦。** 从“全部节目”进入任意单集后继续显示全部单集；
   从某档节目页进入单集后继续保持该档范围。总结、逐字稿和同范围单集导航不会再根据
   URL 所属播客隐式改写用户选择。直接打开或刷新单集深链时，确定性地回退到该单集所属
   播客。
2. **Markdown 链接经过白名单清洗。** `javascript:`、`data:` 等危险协议不再进入
   `dangerouslySetInnerHTML`；内部链接、HTTPS、时间码链接、GFM 表格和标题锚点保持可用。
3. **搜索热路径不再为每个查询重复标准化整库文本。** 首次请求建立进程内轻量索引，
   预先规范化检索字段；每集逐字稿最多收集前 3 个命中，结果进入 64 项 LRU，并为公开
   内容增加 5 分钟 CDN 缓存与 24 小时 stale-while-revalidate。
4. **搜索和移动抽屉正确隔离背景。** 打开搜索时应用壳进入 `inert`；移动抽屉使用模态
   对话框语义并隔离正文。关闭后焦点返回桌面搜索触发器或移动端菜单按钮。
5. **逐字稿在桌面到移动端缩放后不再横向溢出。** `content-visibility` 只声明 block
   轴的固有尺寸，避免浏览器记住桌面 inline 宽度。

### P2：会造成未来发布失败、性能退化或发现性缺口

1. **处理中单集与 Web 发布边界明确。** 只有 `metadata: verified`、总结为
   `draft/reviewed`、逐字稿为 `machine/edited/reviewed` 的单集进入目录、搜索和详情路由。
   合法的 `outline/not-started` 记录可以留在仓库而不拖垮整站构建；一旦达到发布状态，
   缺少总结或逐字稿仍会硬失败。
2. **元数据契约在 Python 与 TypeScript 两端收紧。** 校验 RFC 3339 发布时间、正整数
   时长、`id == show_id:episode_key`、工作流枚举、唯一 ID、唯一首选来源和确定性节目排序。
3. **内容路径增加真实路径边界。** 总结、逐字稿和译稿不能通过 `..` 或符号链接逃出
   单集目录。
4. **时间码契约统一。** 当前明确支持 `00:00:00` 到 `99:59:59`；分钟和秒必须小于
   60，三位小时在升级格式契约前拒绝。
5. **减少无意预取与客户端数据。** 总结页不再自动预取可能达到数百 KiB 的逐字稿 RSC；
   全局客户端壳只接收侧栏需要的轻量单集字段；搜索对话框首次打开时才加载。
6. **补齐搜索与导航可访问性。** 搜索组合框、状态和错误提示具备正确语义；逐字稿数百个
   时间码不再全部占用 Tab 顺序；阅读设置图标不再重复朗读；跳转正文后保留可见焦点。
7. **补齐站点发现性。** 首页、节目、总结和逐字稿都有 canonical、OpenGraph 和
   Twitter 元数据；新增静态 `robots.txt` 与 92 条 URL 的 `sitemap.xml`。
8. **增加 GitHub 质量工作流。** Pull request 与 `main` push 会运行 Python/content 和
   Web 完整门禁，并检查 whitespace。第三方 Action 固定到已核实的完整提交 SHA。
9. **本地阅读偏好在首次绘制前生效。** 根布局用同步的预 hydration 脚本恢复侧栏折叠、
   字号和行宽，继续保持全部内容静态预生成；React 状态和跨标签页 storage 事件会同步
   `<html>` 属性，返回读者不再先看到默认布局再发生列宽与长逐字稿重排。

## 性能结果

搜索基准使用同一 production build 和同一组查询；完整方法见
[Web 阅读器性能基准](./web-performance.md)。

| 指标 | 修复前 | 修复后 | 结果 |
| --- | ---: | ---: | ---: |
| 不同关键词热查询平均响应 | 119.79 ms | 3.55 ms | 降低 97.03% |
| 重复查询 | 需再次扫描 | 1.22 ms | 命中 LRU |
| 冷查询 | 198.67–207.29 ms | 183.12 ms | 首次仍需建索引 |
| 搜索函数追踪内容 | 188 文件 / 14.59 MiB | 143 文件 / 7.74 MiB | 体积降低 47.0% |
| ASR 中间稿进入函数包 | 45 文件 / 6.86 MiB | 0 | 完全排除 |

采样查询的响应字节逐项一致，仍保留 24 条结果上限与逐字稿时间码。进程 RSS 样本没有
显示可靠下降，因此本轮不宣称内存收益；主要收益是热查询 CPU、响应时间和函数包体。

## 仍需后续治理

1. **ASR 供应链可复现性。** 当前批处理仍可使用未固定 revision 的模型别名和第三方
   Hugging Face 镜像。后续应记录 resolved commit、关键文件哈希，并在续跑时拒绝 lineage
   不一致；这是生产流程迁移，不在本轮 Web/内容兼容修复中冒险切换。
2. **全局转写纠错规则。** 少数姓名和缩写替换不是上下文无关真理，应迁移为按单集、可审计
   的 correction map，并记录规则版本与命中；迁移前不批量重写现有正式稿。
3. **搜索规模阈值。** 当前 43 集的进程内索引足够快；达到数百集后，应以冷启动、RSS 和
   p95 为门槛评估构建期倒排索引或外部搜索服务，而不是提前引入复杂基础设施。
4. **自动浏览器回归。** 本轮使用真实浏览器人工回归核心路径；仓库仍应补一套小型端到端
   测试，长期锁定来源范围、模态焦点、窗口缩放、文字复制和控制台错误。
5. **分支保护。** 工作流文件已加入仓库，但 GitHub 端仍需把两个质量 job 设为 required，
   才能阻止未通过门禁的合并。
