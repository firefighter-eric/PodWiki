# 黄东旭：Agent 的长期记忆，会重写数据与软件基础设施

> 状态：`draft`。本文依据发布者简介和[完整 Qwen3-ASR 机器逐字稿](./transcript.zh-CN.md)整理，时间码来自当前正式机器稿。关键片段尚未逐段核听；产品能力、用量、团队效率、市场规模和组织影响尚未独立核查。节目涉及个人数据长期保存、云端记忆与模型自主判断，实际产品仍须满足明确同意、最小化收集、删除权、加密、隔离和安全评估要求。

## 一句话总结

黄东旭认为，Agent 从 Prompt、Context 走向 Harness Engineering 后，核心约束不再只是模型智力，而是如何让单个与多个 Agent 在长任务里保存、提取和同步记忆；这会把数据形态从中心化大数据变成“海量的小数据”，并催生面向 Agent 的数据库、沙箱、身份、通信和支付基础设施，但关于全量留存、云端优先和模型自我评估的主张仍有重要隐私与可靠性边界。

## 为什么值得听

- 它把 Prompt、Context 与 Harness Engineering 串成三代递进关系，并把 compaction 引起的失忆定位为多 Agent 系统的基础问题。
- 访谈从数据库视角提出“一虾一库”：接口上每个 Agent 拥有独立空间，底层以共享存储和虚拟化摊薄成本。
- 后半段进一步讨论经典接口、向量数据库、Unix 组合性、人与 Agent 分工及组织结构，呈现一套完整但需要验证的基础设施假说。

## 核心观点

| 系统层 | 承担的记忆职责 | 设计方向 | 未解决风险 |
| --- | --- | --- | --- |
| Context | 当前任务的短期工作集 | Prompt、工具结果与有限窗口管理 | 压缩后遗忘、窗口耗尽、错误累积 |
| Memory | 跨会话的长期事实与经验 | 检索、重排、时间与来源标注 | 过期信息、隐私、删除与投毒 |
| Harness | 多 Agent 的任务与信息同步 | 角色、子任务、外部记忆、验证 | 协调成本、失控和不可观测性 |
| Agent Infra | 持久化与运行环境 | 独立逻辑空间、共享底座、沙箱和经典接口 | 租户隔离、成本、安全与治理 |

### 1. 从 Prompt 到 Context，再到 Harness，是任务长度和组织复杂度的递进

- **Prompt Engineering**：在短对话里用 Few-shot 和措辞改善即时回答，基本不涉及复杂工具调用。
- **Context Engineering**：任务跨越更多轮次并接入工具，重点变成如何在有限窗口内组织历史、结果和下一步输入。
- **Harness Engineering**：多个 Agent 分工协作，需要同步信息、管理子任务、处理各自的上下文压缩，并接入外挂记忆。
- **边界**：嘉宾把 Harness 类比为管理软件团队，是当前实践框架，不代表多 Agent 系统已经形成稳定工程范式。

### 2. Compaction 解决窗口容量，却可能制造“灾难性失忆”

- **嘉宾主张**：长任务装不进上下文时会压缩历史，但压缩可能丢掉关键约束；对单体 Agent 已经危险，多 Agent 还会把遗漏传播到其他子任务。
- **短期与长期**：Context window 像脑内短期记忆，Memory 像外部笔记本；系统需要先从长期库找到相关事实，再送回当前窗口。
- **价值判断**：通用模型趋同时，用户与 Agent 共同积累的记忆可能成为更有差异性的资产。

### 3. 记忆系统的难点不是只存下来，而是决定记什么、取什么

- **嘉宾方法**：先按相关性检索，再附上信息距离当前时间的标签，把候选交给大模型判断重要性；摘要和知识关系也尽量让模型生成。
- **软件哲学**：与其为每种情形手写复杂规则，不如把模型当成评估函数，围绕它构建 Agent-native 软件。
- **风险边界**：模型判断可能受提示注入、偏差、幻觉、过时信息和对抗数据影响；“让模型自己判断”不能替代访问控制、确定性策略、可审计规则和独立安全评估。

### 4. Agent 数据不是单一大库，而是“海量的小数据”

- **嘉宾主张**：单个用户的文本、文件和对话量远小于传统互联网平台的 PB 级中心化数据；但每个人、每个 Agent 都拥有独立记忆后，系统会面对数量极多的小数据集合。
- **基础设施含义**：优化目标从单库极限吞吐转为大规模租户创建、隔离、生命周期和低单位成本。
- **价值推演**：多模态模型可以把非结构化足迹转成结构化信息，使原本难以利用的个人数据更容易参与个性化服务。
- **边界**：数据“有价值”不等于平台应默认永久保存；收集目的、用户同意、数据最小化、保留期限和可删除性必须先于商业化。

### 5. “一虾一库”是在独立体验与共享成本之间做虚拟化

- **接口层**：每个用户或 Agent 看到一个独立数据库空间，并拥有自己的数据边界与密钥。
- **实现层**：底层使用共享的云存储和数据库虚拟化，让轻度用户不必承担一套专属基础设施成本。
- **产品理由**：Agent 只需理解“这是我的数据库”，不必注册并拼装多个存储服务；经典抽象降低了模型操作基础设施的难度。
- **安全边界**：逻辑隔离不自动等于安全隔离；密钥管理、租户逃逸、备份、恢复、审计和供应商控制权需要独立设计和验证。

### 6. 云端记忆的商业价值首先来自连续性，长期可能来自知识分发

- **近期模式**：为记忆提供备份、恢复、导入导出和托管订阅，解决本地 Agent 升级或故障造成的数据丢失。
- **长期设想**：领域专家与 Agent 长期交流形成的知识，可以被抽取为可外挂的记忆，并通过市场分发给其他 Agent。
- **边界**：嘉宾明确偏向云端体验，但本地、云端或混合方案应由威胁模型、监管、延迟、可携带性和用户选择决定；专家记忆变现还涉及版权、同意、来源和收益分配。

### 7. 基础设施的最终用户从开发者变成 Agent

- **嘉宾主张**：现有云、数据库和网络围绕人类开发者设计；Agent 需要按任务创建的沙箱、极低成本的持久化空间，以及原生身份、鉴权、通信和支付。
- **规模约束**：若数百万乃至更多 Agent 都按传统数据库实例计费，单位成本无法成立，底层实现必须重新设计。
- **接口不变**：模型由人类代码和文档训练，SQL、文件系统、命令行等经典心智模型仍最熟悉；变化更可能发生在接口下面的实现。

### 8. 向量检索会成为数据平台能力，而非独立终局

- **嘉宾主张**：记忆检索同时需要向量、全文匹配和原始字段过滤；把数据拆到多个专用系统会增加 Agent 交叉查询的复杂度。
- **终局判断**：向量能力更可能收敛为数据库或数据平台的标准功能，Agent 看到统一接口，底层再组合多种检索机制。
- **边界**：这是产品架构判断；独立向量系统在超大规模、专业索引、运维隔离或特定延迟目标下是否仍有价值，需要具体工作负载验证。

### 9. 多 Agent 的突破可能来自协同，但 Scaling Law 仍是开放问题

- **嘉宾猜想**：单体 Benchmark 无法覆盖组织能力；一百、一千或更多 Agent 能否像人类社会一样通过分工扩展能力，可能存在尚未识别的规律。
- **工程抓手**：Unix 式简洁接口和可组合工具，比固定图形界面更适合需求多变的 Agent；人类应关注架构、需求和验收，而不是介入每一行代码。
- **组织预测**：未来团队可能由 Harness Engineer、Agent 团队与领域专家组成更小的业务部落。
- **边界**：多 Agent 也可能放大错误、沟通开销和不可观测性；节目中的效率、代码比例、裁员和组织终局均为个人经历或预测，未形成普遍证据。

## 5 分钟读完

这期访谈把 Agent 软件的演进分成三层。Prompt Engineering 优化短对话，Context Engineering 管理长任务和工具结果，Harness Engineering 则组织多个 Agent，并为每个子任务处理同步、压缩和外部记忆。黄东旭把它类比为带一支不睡觉的软件团队：模型能力只是起点，任务分解、上下文和协作机制才决定能否持续交付。[00:03:30] [00:04:06] [00:04:50] [00:05:41] [00:07:30]

记忆成为核心，是因为固定上下文窗口无法容纳现实世界的无限任务。Compaction 能腾出空间，却可能删掉关键约束；长期记忆因此像外挂笔记本，需要在恰当时机检索、筛选并送回短期窗口。节目主张用大模型本身判断信息的重要性，而不是把所有逻辑写成规则。不过，这只适合作为候选排序或辅助判断，安全、权限、删除和审计不能交给模型自由发挥。[00:09:15] [00:10:28] [00:11:13] [00:13:00] [00:15:18] [00:15:41]

从数据库角度看，Agent 产生的是“海量的小数据”。单个人的对话和文件不算大，但每个人、每个 Agent 都形成独立记忆空间后，系统要管理极多租户、密钥和生命周期。“一虾一库”因此不是为每只 Agent 启动昂贵物理实例，而是让它在接口上拥有独立数据库，底层用共享存储和虚拟化摊薄成本。真正难点从单库吞吐转成隔离、创建速度、备份和单位成本。[00:17:28] [00:18:14] [00:19:30] [00:23:29] [00:24:13] [00:24:46]

商业化先从连续性开始：本地 Agent 出故障时，云端记忆可恢复；导入导出、备份和托管可形成订阅。更远的设想是把厨师、律师等领域专家与 Agent 共同积累的经验抽取为外挂记忆，在市场中分发。但这条路不能只看数据价值，还必须回答用户是否同意、谁拥有衍生知识、如何撤回、如何防止跨租户泄露，以及本地和混合部署是否更适合敏感场景。[00:25:33] [00:26:33] [00:27:16] [00:27:51] [00:28:17]
