# 江鋆晨：KV Cache 不只是缓存，而是模型原生的记忆数据层

> 状态：`draft`。本文依据发布者简介和[完整 Qwen3-ASR 机器逐字稿](./transcript.zh-CN.md)整理，时间码来自当前正式机器稿。关键片段尚未逐段核听；技术性能、产品能力、客户采用、公司竞争力和市场预测尚未通过论文、代码、基准或独立来源核查，不代表已完成人工审核。

## 一句话总结

江鋆晨把 KV Cache 从“一次推理后可以丢弃的中间状态”重新定义为模型原生的记忆数据：第一层复用计算，第二层在不改变语义的前提下压缩、拼接或跨场景复用，第三层则主动修改注意力并影响输出；TensorMesh 的机会在于用同时懂系统与机器学习的软件层，把这种数据接入企业共享知识、冷热存储和未来的分布式推理。

## 为什么值得听

- 它从 Prefill、Decode 与定价差异切入，解释为什么用户感觉“输出更贵”，输入侧却可能承担同样甚至更大的总计算量。
- “黑盒状态—语义数据—模型操作层”的三层框架，把缓存、压缩、质量优化和模型行为连接到同一条技术路线。
- 访谈没有停在 GPU 内存，而是进一步讨论企业共享知识、非前缀复用、冷热分层、跨数据中心分发和架构变化。

## 核心观点

| 理解层 | KV Cache 是什么 | 可做的操作 | 主要挑战 |
| --- | --- | --- | --- |
| 第一层 | 可保存的计算状态 | 存储、取回、相同前缀复用 | 容量、传输、命中率和工程集成 |

### 1. Agent 把推理瓶颈从“生成速度”扩展到输入与记忆管理

- **嘉宾主张**：Agent、长对话和长文本让输入越来越长；模型每次都重新读上下文，不只消耗 GPU 计算，也生成越来越大的中间记忆。
- **系统问题**：硬件资源与 workload 不再匹配，单靠更强 GPU 或改模型不足以解决；软件需要决定哪些状态保留、放在哪里、何时复用。
- **产品定位**：TensorMesh 和 LMCache 试图保存模型读完上下文后的 KV Cache，在相同或相近上下文再次出现时减少重复 Prefill。

### 2. 输入便宜是定价与延迟造成的错觉，不等于计算量小

- **嘉宾主张**：按单 Token 计算量看，处理输入和生成输出并没有数量级差异；Prefill 能大规模并行，所以等待时间较短，Decode 逐 Token 生成，用户更容易感知其延迟。
- **总量效应**：Agent 每轮都附带更长历史，输入可能远长于输出，因此输入侧总计算量可能更高，即使 API 标价更低。
- **边界**：具体成本还取决于模型架构、批处理、硬件利用率、服务商调度和计费策略；节目中的概括不应替代实测。

### 3. KV Cache 的三层理解，从复用计算走向编辑模型记忆

- **第一层**：把 KV Cache 当黑盒计算状态，原样存储并在同样前缀出现时复用，这是当前最直观的工业实现。
- **第二层**：把它视为包含注意力和语义信息的白盒数据，只要语义保持，就可以有损压缩、更新，甚至尝试跨文本或跨模型复用。
- **第三层**：主动改变其中语义与注意力，让模型更关注或忽略某些内容，从而影响输出质量。
- **边界**：第二、第三层的可行性、精度损失、跨模型条件和安全风险需要以具体论文、代码与基准验证；这里记录的是嘉宾提出的路线。

### 5. 企业共享知识，是模型原生记忆最直接的复用场景

- **场景**：代码库、政策文档、法律与金融材料会被多个 Coding Agent、内部 Chatbot、RAG 和多模态应用反复读取。
- **价值主张**：把已经处理过的知识保存为模型可直接读取的状态，可以减少重复 Prefill；长期还可能通过重新强化文本中间的重要内容，缓解长上下文的 `lost in the middle`。
- **第三条路**：在不改模型权重、也不改 Prompt 文本的前提下，优化模型对 Prompt 的内部理解。

### 6. 非前缀复用使存储层变成带计算的服务

- **嘉宾主张**：传统 Prompt Cache 主要复用相同前缀；当可复用内容位于输入中间时，KV Cache 必须更新后才能与新的前文关系匹配。
- **系统含义**：所谓 Cache Blend 不只是搬运数据，还需要在存储服务里做计算；存储层因此需要理解上下文结构，而非充当透明的字节仓库。
- **多模态延伸**：图片和视频会展开成极长 Token 序列，同时包含大量语义冗余，使压缩、跨分辨率复用和任务相关表示成为新的研究空间。

### 7. “以存代算”成立与否，取决于传输、重算和命中率的动态权衡

- **嘉宾主张**：当 KV Cache 位于 CPU 内存、本地 SSD 或高速直连存储时，取回可能比 GPU 重算更快，因此可以同时降本和降延迟；放得越冷、越远，传输延迟越可能抵消收益。
- **分层策略**：热数据靠近 GPU，冷数据下沉，但什么会在下一秒、明天或每天固定时间被复用，往往只有业务 operator 知道。
- **产品原则**：系统应提供接口表达业务侧的 domain knowledge，而不是完全透明地替客户决定所有冷热策略。

### 8. 从数据中心内的 mini CDN，走向模型原生的知识分发网络

- **类比**：CDN 把网页和视频内容放到接近用户的位置；KV Cache 分发则把模型需要的记忆状态放到接近推理引擎的位置。
- **当前阶段**：多数推理集中在单一数据中心，因此产品更像数据中心内部的 mini CDN。
- **长期推演**：若 Agent 对延迟更敏感、推理走向边缘和多数据中心，模型与模型之间距离增大，可能需要 Internet-scale 的 Knowledge Delivery Network。
- **边界**：跨数据中心和边缘推理的时间表属于嘉宾长期预测，过去数年尚未按其早期设想快速发生。

### 9. Token 越多，不代表利用越好；关键是选择性复用

- **嘉宾主张**：当前 Agent 常把所有历史和输出原样塞回 Context，Token 消耗快速增长，却不一定带来等比例价值。
- **优化方向**：压缩不是唯一答案；系统还要判断哪些内容值得保留、哪些状态可以复用，尤其是如何处理非前缀知识。
- **市场判断**：未来模型生态可能像在线视频而非搜索，由少数巨头和多个垂直、私有或主权模型并存；而“模型原生中间状态”也不局限于 Transformer，Mamba、Diffusion 等架构仍会产生其他形式的状态。

## 5 分钟读完

Agent 时代的上下文会随任务进展不断增长，而模型本身是无状态的：每次调用都要重新读取历史、文档和工具结果。江鋆晨认为，这让推理瓶颈不再只是 Decode 的生成速度，还包括 Prefill 的重复计算与由长上下文产生的大量中间状态。TensorMesh 所做的“记忆管理”，就是把这些通常在一次请求后被丢弃的 KV Cache 保存下来，供后续请求复用。[00:01:05] [00:02:09] [00:02:35] [00:03:45]

为什么要优化看似便宜的输入？节目区分了价格、延迟和计算量：Prefill 并行度高，用户等待短；Decode 串行生成，等待更明显，因此服务商通常把输出 Token 定价更高。但按单 Token 的底层计算看，输入未必便宜，而 Agent 的输入长度又常常远超输出。若每轮都重新处理相同知识，低单价仍会累积成显著的 GPU 成本。[00:04:06] [00:05:10] [00:05:45] [00:06:10] [00:06:26]

访谈最重要的贡献是“三层理解”。第一层把 KV Cache 当可复用的黑盒计算状态；第二层承认它包含注意力和语义，可以在语义保持的条件下压缩、更新或跨场景复用；第三层则直接修改注意力，让模型重新关注文本中的重要部分并影响输出。由此，KV Cache 从缓存升级为模型原生数据层，潜在价值也从降本提速延伸到质量优化。[00:08:55] [00:09:23] [00:10:10] [00:10:27] [00:11:16]

最直接的企业场景是共享知识：同一代码库、政策、合同或客服资料会被多个应用和 Agent 重复读取。若这些知识以模型已经处理过的状态保存，就能减少重复 Prefill。难点在于，真正有用的内容不一定出现在相同前缀；非前缀复用要求更新 KV Cache，使存储层同时具备计算和语义理解。这也解释了为何该方向需要系统工程与机器学习交叉，而不是单纯增加存储容量。[00:15:39] [00:16:15] [00:18:10] [00:20:01] [00:22:29] [00:23:08]

经济账是“重算还是搬运”。热 KV Cache 放在靠近 GPU 的内存或高速存储，取回可能比重算更快，做到降本与提速；越冷、越远的介质成本更低，却增加传输延迟。更重要的是，冷热判断带有业务规律，operator 可能知道某份知识何时再次使用。江鋆晨因此主张开放策略接口，让客户把 domain knowledge 带进分层与调度，而非由系统完全黑盒决定。[00:28:42] [00:29:05] [00:29:41] [00:30:31] [00:31:18]

长期看，这套系统可类比 CDN。眼下推理大多集中在一个数据中心，KV Cache Storage 更像内部 mini CDN；若 Agent、边缘推理和低延迟需求推动模型靠近用户，未来可能出现跨数据中心的“知识分发网络”。即使 Transformer 被混合架构替代，嘉宾认为真正管理的也不是特定名词，而是各种模型在运行中生成的中间状态。这个愿景能否成立，仍取决于命中率、传输带宽、压缩精度、模型质量和真实客户工作负载的共同验证。[00:32:31] [00:33:30] [00:35:04] [00:35:42] [00:42:18]
